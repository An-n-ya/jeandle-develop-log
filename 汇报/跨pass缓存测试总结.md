# 跨 pass 缓存测试总结

整理日期：2026-10-27。覆盖 2026-10-23 至 2026-10-27 的相关实验。

**目前可以确认：缓存能跨 pass 复用，也确实减少了一些重复计算。但在本次完整流水线测试中，还没有证明整体编译变快；与每个 pass 清缓存相比，本次还测到小幅变慢。**

本文先说明为什么测试，再说明怎么测试、测到了什么。详细命令和原始记录放在文末链接中。本次整理核对了报告和关键原始数据，没有重新运行性能测试。

## 1. 为什么要做这些测试

编译器会经过多个优化步骤，每个步骤叫一个 pass。TCE、CHA、CFF 和 RecoverTypeInfo 都可能调用 getJavaType，询问同一个值的 Java 类型。

我们希望前一个 pass 算出的结果，后一个 pass 还能继续使用。例如：TCE 已经查过一个对象的类型，RecoverTypeInfo 随后处理该对象的字段时，就不必重新计算。

这个目标包含两个不同问题：

- **能不能复用？** 缓存是否真的留下来，后面的 pass 是否真的读到了它？
- **值不值得复用？** 省下的计算，是否足以抵消保存、查表和清理缓存的成本，让整个编译过程更快？

早期测试不容易把这两个问题分清。增加调用点时，测试也会不断加深控制流；LVI 用来判断路径条件和空指针边的工作会变重。同时，许多测试每查询一次就修改 IR，上下文缓存很快失效。这些测试能观察 Base 是否保留，却不容易观察连续读取和跨 pass 共享的收益。

因此，后续测试分成两步：先用小用例验证复用，再把输入放进完整生产流水线，测量总成本。

## 2. 测试中几个名称是什么意思

| 名称 | 直白解释 |
| --- | --- |
| Base | 只根据值本身和它依赖的表达式计算出的基础类型 |
| PathFacts | 走到某个基本块时，由路径条件带来的类型信息 |
| Final | 某个值在某个基本块的最终查询结果 |
| 命中 | 直接使用已经算好的结果 |
| 失效 | IR 改了，旧结果可能不再成立，需要删除或放弃 |
| preserve | pass 告诉分析管理器：相关分析结果在修改后仍然有效，可以继续保留 |

Base 插入次数减少，可以说明缓存的重复填充减少；它不等于底层函数调用次数。缓存失效也不一定是问题：当旧结果已经不可靠时，失效是必须的。

## 3. 我们怎样区分收益来源

完整流水线实验使用三种模式：

| 模式 | 做法 | 用来回答的问题 |
| --- | --- | --- |
| ORIGINAL：原始查询 | 使用当前程序中的原始查询路径，关闭跨查询 JavaType 缓存 | 整个缓存方案相对原始查询有没有收益？ |
| PASS-LOCAL：只在 pass 内缓存 | 一个 pass 内正常使用缓存；下一个消费者 pass 开始时清空已有条目 | 只靠 pass 内复用能做到什么程度？ |
| CROSS-PASS：允许跨 pass 缓存 | 按当前的修改通知和失效规则保留缓存 | 跨 pass 共享额外贡献了多少？ |

比较 ORIGINAL 和 CROSS-PASS，观察整个缓存方案的效果；比较 PASS-LOCAL 和 CROSS-PASS，观察跨 pass 共享的额外效果。这两组百分比不能相加。

ORIGINAL 是当前二进制中的原始查询路径，不是把所有代码退回缓存改动前。因此，本轮也不能直接代表所有历史版本差异的收益。

## 4. 第一轮：先证明后一个 pass 确实用了旧结果

第一轮使用小型 IR 用例，控制查询对象、基本块和修改位置，避免把所有因素混在一起。

### 4.1 同一个 pass 内，重复查询可以命中

TCE 在同一个基本块中连续查询同一个对象 4 次：第一次计算，后面 3 次直接命中 Final。

把这 4 次查询放到不同的浅层基本块后，Final 的键不同，不能直接共享，但 Base 只插入一次。这说明不同层的缓存分别发挥了作用。

零重叠对照中，4 次查询使用 4 个不同对象，没有命中，Base 插入 4 次。测试没有把不该复用的查询误算成命中。

### 4.2 TCE 不修改 IR 时，RecoverTypeInfo 能直接使用它的结果

用例顺序是：TCE 查询，然后 RecoverTypeInfo 查询同一个对象。

| 模式 | 全部查询数 | Final 命中 | Base 插入 | RecoverTypeInfo 的第一次查询 |
| --- | ---: | ---: | ---: | --- |
| 只在 pass 内缓存 | 4 | 2 | 2 | 重新计算 |
| 允许跨 pass 缓存 | 4 | 3 | 1 | 直接命中 TCE 留下的结果 |

最重要的证据是“下一个 pass 的第一次查询就命中”。它排除了另一种情况：下一个 pass 自己先计算一次，然后只是在自己的内部复用。

### 4.3 TCE 修改 IR 后，一部分结果仍然可以保留

另一个用例让 TCE 折叠类型检查。修改后，相关 Final 被删除，但对象本身的 Base 仍然有效。

- 只在 pass 内缓存：到 RecoverTypeInfo 时再次插入 Base，累计 2 次。
- 允许跨 pass 缓存：RecoverTypeInfo 使用留下的 Base，累计只有 1 次。

这证明了“有修改”并不一定要清掉所有结果。选择性失效可以保留仍然有效、并且确实会被后面使用的条目。

### 4.4 四个消费者都测到了，但保留能力不同

TCE→CFF 和 CFF→TCE 的无修改用例也能跨 pass 命中。CHA 和 RecoverTypeInfo 都有实际查询记录。

不过，当前 CFF 和 RecoverTypeInfo 在发生修改后，不会保留整个 JavaTypeAnalysis。下游会重新建立分析。RecoverTypeInfo 新写出的 metadata 能帮助 CHA 优化，但这是“新类型信息带来的收益”，不能算成“旧缓存被复用”。

第一轮新增 14 个 lit 测试全部通过。原有测试中仍有已记录的失败和工具缺失，所以结论是“新增测试通过”，不是“整个仓库全部通过”。

第一轮的短进程计时波动较大，没有据此给出加速结论。

## 5. 第二轮：把查询放进完整生产流水线

第二轮使用完整的 `jeandle<O3>`，保留正常内联、默认开启的 PEA、标准 LLVM 优化和 GC 相关处理。没有为了提高命中率删掉中间 pass。

可以把这条流水线理解成：

```text
前端 IR
→ 类型恢复、类型检查消除、常量折叠和清理
→ 去虚化、内联及内联后的清理
→ PEA 和循环相关优化
→ 再次类型恢复、检查消除和折叠
→ 完整 O3、GC 与后续降低
```

输入来自 6 个专门编写的 Java 程序，覆盖数组、集合、字段、类型检查、内联和负对照场景。录制得到 76 份方法编译记录，其中 64 份可用于比较；另 12 份在原始模式回放时失败，被排除。

**这里使用的是真正的 Java 编译入口和生产流水线，但输入仍是合成程序，不是实际应用负载。** 64 份记录中也包含运行这些程序时编译到的 JDK 方法，不能称为 64 个独立应用。

每份输入分别运行三种模式，共做 2 组独立测量，每组 30 轮随机配对，得到 11,520 条正式计时记录。每次仍单独启动 opt；主指标是包含启动、解析和优化的进程 CPU 时间。另做了扣除无优化运行基线的估算，但没有实现原计划中的进程内批量回放器。

### 5.1 缓存确实减少了重复填充

下面是每遍完整语料的诊断计数，和正式计时分开采集：

| 指标 | 只在 pass 内缓存 | 允许跨 pass 缓存 |
| --- | ---: | ---: |
| 顶层查询数 | 173 | 173 |
| Base 插入次数 | 168 | 100 |
| Final 命中次数 | 0 | 68 |

查询数量没有减少，但 Base 少插入 68 次，Final 多命中 68 次。这说明共享确实减少了重复工作。

按诊断中的消费者分组，这 68 次 Final 命中中，64 次发生在 RepeatedConstantFolding 执行期间，4 次发生在 TCE 执行期间。RecoverTypeInfo 和 CHA 在这批语料中没有 Final 命中；这不等于它们完全没有 Base 或 PathFacts 复用。

### 5.2 整个回放过程没有因此明显变快

下表是每种模式 3,840 次正式回放的累计进程 CPU 时间：

| 模式 | 累计时间 |
| --- | ---: |
| 原始查询 | 87.803 秒 |
| 只在 pass 内缓存 | 87.665 秒 |
| 允许跨 pass 缓存 | 87.967 秒 |

为了避免正负号混淆，下面统一用“耗时变化”：正数表示更慢，负数表示更快。

| 比较 | 允许跨 pass 后的耗时变化 | 95% 置信区间 | 怎么理解 |
| --- | ---: | --- | --- |
| 相对原始查询 | 增加约 0.19% | −0.09% ～ +0.47% | 范围包含零，不能确认有稳定变化 |
| 相对只在 pass 内缓存 | 增加约 0.34% | +0.08% ～ +0.61% | 本次固定语料和测量方法下，测到小幅变慢 |

扣除无优化运行基线后，方向没有变化：分别增加约 0.22% 和 0.41%。这种扣除只是估算，不能当作直接测量的纯优化器时间。

因此，当前数据支持“跨 pass 复用成立”，但不支持“跨 pass 共享已经让整体编译更快”。同样，也不能只凭这一批输入断言每个 pass 都清缓存普遍更好。

## 6. profiling 告诉了我们什么

本轮采集了调用栈，并生成完整火焰图、差分火焰图和成本分解。

### 6.1 这批输入中，JavaType 占总成本很小

按保存的高频采样数据，只合计标记为 JavaType 的分类，每遍语料约为 1.4–1.6 毫秒；整遍回放约为 1.24 秒，JavaType 占比约 0.1%。

这个量级解释了为什么“少算了一些”很难体现在总时间上：即使这部分省掉很多，总体也可能只变化一点点。

不过，十遍语料中落在这些分类的样本合计只有约几十个。它适合说明“JavaType 在这批输入里不是大头”，还不足以精确断言某个很小的函数快了多少。更不能因为火焰图某条栈变窄，就直接认定整个方案更快。

### 6.2 找到了缓存被丢弃的位置，但还没有证明它是性能瓶颈

跨 pass 模式下，诊断记录到 100 次“分析被丢弃时，缓存里仍有条目”，其中 71 次发生在 JavaOperationLower。

这使 JavaOperationLower 成为值得继续检查的位置。不过，该计数没有告诉我们：那些条目在被丢弃之前是否已经被使用、如果继续保留是否还会被访问、又能省多少时间。

所以准确的结论是：**找到了一个主要的缓存保留断点，还没有证明它是导致净收益不足的主要原因。** 修改 preserve 合同前，必须先证明分析能被正确维护，并确认后面有实际需求。

### 6.3 不把局部诊断时间当作总加速

带统计的诊断运行中，查询加失效入口的累计时间，PASS-LOCAL 约为 1.089 毫秒，CROSS-PASS 约为 0.673 毫秒，减少约 38%。

这个数字只描述带统计的局部入口，而且包含 PASS-LOCAL 人为清理产生的开销。它没有覆盖所有相关成本，不能写成“编译加速了 38%”，也不能用它推翻前面的正式进程计时。

## 7. jtreg 和真实 JVM 中测到了什么

### 7.1 jtreg 验证了模式生效和缓存复用

新增的 `TestJavaTypeCacheModes` 通过。它启动真实子 JVM，检查参数确实传入，并验证三种模式的行为。

每种模式均有 98 次查询。PASS-LOCAL 的 Final 命中为 0，CROSS-PASS 为 6；Base 插入从 58 次降到 44 次。

这说明缓存不是只在独立 opt 回放中有效，在 JVM 编译中也会被使用。测试没有要求“必须快多少”，也没有拿整个 jtreg 的 6 秒运行时间作为缓存收益。

### 7.2 固定编译任务后，没有测出稳定加速

受控组固定为单编译线程、一个目标编译任务，做了 15 轮配对。三种模式的平均 LLVM Optimize 时间分别为：

| 模式 | 平均 LLVM Optimize 时间 |
| --- | ---: |
| 原始查询 | 129.4 毫秒 |
| 只在 pass 内缓存 | 131.0 毫秒 |
| 允许跨 pass 缓存 | 129.5 毫秒 |

两组比较的置信区间都包含零。总编译时间和应用运行时间也没有稳定收益。这里的 CITime 是经过时间，不是线程 CPU 时间，且只测试了一个受控目标。

### 7.3 正常后台编译组的数据不能直接归因于缓存

另一组保留正常分层和后台编译。它出现了一些正向百分比，但三种模式实际完成的 Jeandle 编译次数平均为 20.5、21.0 和 20.0 次，工作量不完全相同；后台阶段计时也有并发口径限制。

例如，报告中的“总编译成本下降约 7.16%”不能直接当作跨 pass 缓存收益。少编译了哪些方法也会影响时间，仅除以编译次数不能消除这种差异。

JVM 性能运行还出现了受控组 3 次、后台组 4 次失败重试。基线也复现过崩溃，但这不足以证明每次失败都与改动无关；性能结果应理解为成功完成运行的结果。

## 8. 到目前为止，我们可以怎样汇报

可以使用下面这段表述：

> 我们先通过小型用例确认了跨 pass 复用：下一个 pass 能直接读到前一个 pass 的结果，修改后仍然有效的 Base 也可以继续使用。随后把测试扩展到完整生产流水线和真实 JVM。完整流水线中，Base 插入从 168 次降到 100 次，Final 命中从 0 次增加到 68 次，说明重复工作确实减少了。但这批合成 Java 输入中的 JavaType 成本占比很小，整体计时尚未显示稳定加速；与每个 pass 清缓存相比，本次还测到约 0.34% 的小幅变慢。下一步需要扩大实际应用输入，并检查被丢弃的缓存是否真的会被下游再次使用。

下一步最值得做的三件事是：

1. **换更有代表性的输入。** 加入实际应用的方法，保留低查询和零查询样本，避免只测为了缓存而设计的场景。
2. **把编译时间测得更直接。** 使用进程内独立编译回放，或每次 JVM 编译的局部线程 CPU 计时，减少启动、解析和并发任务变化的干扰。
3. **追踪丢弃后是否真的重算。** 对 JavaOperationLower 等位置记录“丢弃了什么、后面是否又查了它、重算花了多少”，再决定是否值得改 preserve。
