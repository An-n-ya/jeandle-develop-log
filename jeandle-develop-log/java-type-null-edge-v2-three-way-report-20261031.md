## 补充场景的诊断证据

每版本、每场景诊断两批，即 64 次查询。计数不来自正式计时样本。

| 场景 | 版本 | Final hits | Facts hits | 外层 oracle 回调次数 |
|---|---|---:|---:|---:|
| 同 key、无修改 | base | 62 | 0 | 68 |
| 同 key、无修改 | null | 62 | 0 | 0 |
| 同 key、无修改 | v2 | 62 | 0 | 68 |
| 32 个不同上下文、仅一轮 | base | 0 | 62 | 130 |
| 32 个不同上下文、仅一轮 | null | 0 | 62 | 0 |
| 32 个不同上下文、仅一轮 | v2 | 0 | 6076 | 130 |
| 16 个上下文、两轮 | base | 32 | 30 | 98 |
| 16 个上下文、两轮 | null | 32 | 30 | 0 |
| 16 个上下文、两轮 | v2 | 32 | 2460 | 98 |
| 同块无关修改 | base | 62 | 0 | 68 |
| 同块无关修改 | null | 62 | 0 | 0 |
| 同块无关修改 | v2 | 0 | 0 | 2176 |
| 不同块无关修改 | base | 62 | 0 | 68 |
| 不同块无关修改 | null | 62 | 0 | 0 |
| 不同块无关修改 | v2 | 62 | 0 | 2176 |

这些计数揭示了三个需要区分的机制：

1. 旧 null-edge 优化在这些补充输入中可以通过预过滤避免外层 oracle 回调；V2 仍会调用它，不能假设 V2 已继承该优化的全部收益。
2. 旧版 PathFacts 缓存完成的 `(Value,Block)` 结果，跨上下文时可以直接截断递归；V2 的共享缓存是 guard/null 边事实，仍需按查询重建 factsAt 的完成状态。因此两种 Facts hits 的含义不同，不能直接比较命中数大小。
3. 对纯算术无关修改，旧缓存可能直接保留 Final；V2 保守的块依赖可能淘汰它。不同块修改下 V2 即使保留 Final，也要重新验证 null-edge 观察。这些场景里保留 Base 不足以抵消额外工作。

这不意味着可以无条件回退全部新语义。旧版还有已知正确性/精度测试问题，而 V2 修复了其中部分；这里的 guard 与修改序列刻意保证相关类型不变。建议在保持正确性约束的前提下，评估将旧 null-edge 预过滤等价迁入 V2，并优化 Final 准入/依赖维护和低复用路径。

## 正确性与计时口径

- native：五份相同结构 .ll，由单一驱动源码按各版本 API 分别静态链接。每批清空缓存与 LVI，然后进行固定 32 次查询；修改场景在第 2..32 次查询前通知旧 IR、清 LVI、修改无关 add。每个诊断查询与全新 DT/AC/LVI 上该版本的原始 getJavaType 比较完整类型，要求 klass=22；旧版不得 SkipVerification。计时不做差分和可选统计。各版本单独校准批次数来取得足够长样本，比较每批成本；查询序列与冷/热比例固定。它不是三版本相同进程工作量的总 CPU 比较。
- opt：原来五个 workload，仍为各 1024 个独立函数，使用原 cases.json、相同 callback 和 Pass 管线。每版本先分别做 cached/reference 验证与诊断，两者 IR 必须一致，三版本输出 IR 也必须逐字节一致。计时只用 -disable-output，不启用统计/验证；进程重新解析原输入。
- 两类测试均不测 Java 程序运行速度，不代表生产 JVM 总编译性能。本任务未并行构建或运行其他基准，源码分支保持未修改。
