# V2 null-edge 优化与四版本性能复测

日期：2026-11-03。基于上一轮已发布的 `31bdeb46178c`，加入 null-edge 负向预过滤和 unknown 合并短路。

提交 [`6ec57ff43381`](https://github.com/Atm2086/jeandle-llvm/commit/6ec57ff43381edf405ba11cdf3ff3a2b5c3b6e7e) 已推送至 `feat/javatype-final-cache`，本轮测试与发布的是同一提交。

## 结论

相对加入前 V2，**10 / 10 个场景显著改善**：5 个完整 opt 场景成本降低 **16.74%–32.15%**，5 个微基准降低 **36.85%–57.62%**。完整 opt 已全部快于原版 V1 缓存，幅度为 **12.69%–27.93%**。

两项跨上下文微基准比旧 V1 + null-edge 分别快 10.09%、5.17%。完整 opt 仍比旧 null-edge 版慢 2.29%–27.73%，同 key 场景仍慢 23.17%；无关修改场景也仍有明显差距，因为 V2 继续保留 oracle 相关结果的保守失效规则。

## 改动逻辑与边界

1. 将过滤放在 typed `LVINullEdgeOracle` 中，仅在显式传入单次查询状态时启用。`JavaTypeAnalysis` 每次查询创建新状态；原单参数 oracle 和自定义回调的行为保留。
2. 使用有界的 use/definition 检查排除不可能提供 null 证明的查询。别名、cast、zero GEP、freeze、PHI/select、returned 参数等均保守处理；比较、整数转换、未知形状、环或上限触发时仍调用原 LVI。
3. PHI/select 对可能的 null 来源采用保守 OR；不要求两臂都可折叠 null。未证明安全的 freeze 不会被额外剥离。扫描预算为 256 步，定义深度上限为 64；上限仅决定是否回退 LVI，不取消 LVI 证明。
4. 共享 facts 求解器在 union 结果变成完整 unknown 后停止遍历剩余前驱。缓存、PHI 环、预算和 IR/oracle 失效规则不变。
5. 新增独立的请求、结构回答、过滤、实际 LVI 调用和限额回退计数；只在诊断中收集。cache verification 使用未过滤的 oracle。未启用旧实验性块级 LVI，也未加会改变精度的新 oracle 调用上限。

详见[设计说明](artifacts/v2-null-edge-optimization-20261103/after/JeandleNullEdgePrefilter.md)及[完整补丁](artifacts/v2-null-edge-optimization-20261103/optimization.patch)。

## 正确性与审计

- **91 个单元测试全部通过**，含新增七项真实 LVI 测试。
- 扩展 Pass 回归 146 项中 **145 项通过、1 项因 Release 未启用 asserts 而不适用**：java-type-metadata-recovery/recover-fixpoint-oscillation.ll。后端 clone-expansion、OSR char-arraycopy 及其他依赖 null 边精度的用例通过。
- 每版本、每 native 场景 64 次诊断查询，逐次对照新建 DT/AC/LVI 的未过滤原始完整 JavaType，要求 class 22；V1 不得跳过验证。20 组 native 诊断/输入检查通过。
- 四版本最终 opt IR 逐字节一致，每版本 verification 与 diagnostic IR 也一致；输入哈希与前一轮相同。
- 计时关闭统计与差分验证。CPU 8 / SMT 兄弟 9，不更改 governor 或服务，移除 LD_LIBRARY_PATH。
- 每场景先 3 轮预热 + 15 对 V1/V1 A/A，再 3 轮预热 + 31 轮四版本随机串行交错，种子 20261103。native 分版本校准批次数至约 360ms CPU。
- 4000 次 bootstrap 的 95% CI 须完全越过该行 A/A 绝对变化 P95，且所有正式样本 >=200ms CPU，才判改善/回退。
- **1540 个正式样本，最短 CPU 246.60 ms**；所有二进制哈希在结束后再次核对，源码分支干净，补丁反向检查通过。本机再次独立复核 10 组成本中位数、60 组配对变化、9 份源码及驱动哈希和 5 项开关对照，全部一致。
