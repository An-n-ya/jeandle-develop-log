# 跨 pass 缓存报告：口径核对说明

整理日期：2026-10-27。阅读主文：[跨 pass 缓存测试总结](../汇报/跨pass缓存测试总结.md)。

本文用于解释整理版与原始执行报告的措辞差异。原方案和报告继续保留，便于追溯；本文没有改动被测程序，也没有重跑性能实验。

本次只读核对了本地报告，以及服务器 `/home/annya/playground/jeandle/perf-results/2026-10-26-javatype-cross-pass-prod/` 下的关键 CSV、JSON 和统计脚本。对主性能置信区间沿用原统计结果，没有重新生成区间。

## 1. 已复核的主要数据

### 1.1 正式进程计时

直接读取 `timing/raw.csv` 得到：

| 模式 | 正式运行数 | 失败数 | CPU 累计秒 | 平均每次毫秒 |
| --- | ---: | ---: | ---: | ---: |
| original | 3840 | 0 | 87.803128 | 22.865398 |
| pass_local | 3840 | 0 | 87.665248 | 22.829492 |
| cross_pass | 3840 | 0 | 87.967407 | 22.908179 |

共 11,520 条正式记录。`timing/baseline.csv` 有 640 条无优化运行记录；按每个 session／sample 取五次中位数后，这些中位数的平均值为 **3.820906 毫秒**。

原报告 §6.2 把启动和解析写为约 22 毫秒、占主要部分，与上述基线不一致。约 22.8 毫秒是整个 opt 运行的平均 CPU 时间；无优化运行基线约占其 17%。基线也包含 opt 的其他固定工作，不能进一步全部归为纯解析。

`scripts/timing.py` 中无优化命令是不带 pipeline 的 opt。两次独立进程时间相减是估算，无法完全消除频率、调度、callback 加载和不同执行路径的影响。因此整理版称“进程回放时间”，不称“直接测得的纯优化生命周期时间”。

报告中每轮约 1.22 秒的扣基线工作量低于方案建议的 2–10 秒，不能写成处于该区间内；它是整份语料的总和，也不是单个长进程的持续测量。

### 1.2 性能变化的符号

原统计公式是 `节省比例 = 1 - 候选时间 / 基线时间`，负数表示变慢。

| 对照 | 原口径：节省比例 | 整理版：耗时变化 |
| --- | --- | --- |
| original → cross_pass | −0.1871%，CI [−0.4700%, +0.0888%] | +0.1871%，CI [−0.0888%, +0.4700%] |
| pass_local → cross_pass | −0.3447%，CI [−0.6075%, −0.0833%] | +0.3447%，CI [+0.0833%, +0.6075%] |

远端 `timing/summary.md` 的第二组结论自动写成“测出稳定净收益”，与其负号方向相反；本地详细执行报告已经说明是变慢。整理版保留本次小幅变慢的结果，同时限制在该语料和测量方法内，不推广成“pass-local 普遍最优”。

### 1.3 诊断计数

`diagnostics/cross_pass_trace_summary.json` 确认：

- 两个缓存模式的顶层查询均为 173。
- Base 插入：168 → 100；Final 命中：0 → 68。
- 真实 selective invalidations 两边都是 32。
- PASS-LOCAL 另有 13,154 次测试策略主动 clear；其失效请求总数因此为 13,186。

“失效请求从 13,186 降到 32”不能解释成生产 IR 修改减少了 99% 以上。差额来自人为定义的清理对照，也不代表每次 clear 都删除了有效条目。正式比较可以包含这些成本，但汇报必须说清来源。

Base 插入是计数器定义，不等价于完整底层递归调用次数。ORIGINAL 的 Base／Final 计数为零表示绕过了缓存计数，不表示没有做类型计算。

消费者归属中，RepeatedConstantFolding 64 次、TCE 4 次是 Final 命中分布。RecoverTypeInfo 和 CHA 没有 Final 命中，不能扩大为“没有任何种类的缓存复用”。阶段归属也不等于每个条目的完整创建／消费履历。

## 2. profiling 的结论需要限制到什么程度

`profiles/cost_decomposition.json` 的每轮权重中，仅合计 `jta_*` 项得到：

| 模式 | JTA 分类合计 | 总采样估计时间 | 比例 | 十轮约对应的 JTA 样本数 |
| --- | ---: | ---: | ---: | ---: |
| original | 1.434 ms | 1243.913 ms | 0.115% | 43 |
| pass_local | 1.634 ms | 1246.480 ms | 0.131% | 49 |
| cross_pass | 1.534 ms | 1248.614 ms | 0.123% | 46 |

原报告列 cross_pass JTA 合计为 1.601 ms，是额外合入 0.067 ms 的 `vm_callback` 分类后的数字。整理版统一口径，仅用 `jta_*`，正文表述为约 1.4–1.6 ms、约 0.1%。

这些值是采样权重换算，不是纳秒精度的直接函数计时。JTA 分类样本很少，细分 Base／LVI／维护时更少；不能据此可靠排序数十微秒的差异。定向子集也只有约百余个 JTA 样本，应保留其统计限制。

带统计入口的 `subsystem_cost.json` 显示 PASS-LOCAL 的 query＋invalidation 约 1.089 ms，CROSS-PASS 约 0.673 ms。它来自打开 stats 的独立运行，包含人工清理入口，且不覆盖所有构造、销毁及依赖分析工作；约 38% 的局部下降不能当作整体性能结论。

部分高频和 JVM 定向 profiling 原始 perf.data／script 已按执行报告清理。保留的 JSON／folded／SVG 可以用于说明，但不是全部原始采样证据仍然完整。需要深入复核相应采样时，应重采并保留原始文件。

## 3. JavaOperationLower 是断点，不是已经证实的瓶颈

`profiles/pass_invocation_timeline.json` 中，cross_pass 的 `analysis_lifetime_with_entries` 合计为 100 次，其中 JavaOperationLower 为 71 次。

它统计的是“分析被丢弃时还有条目”的次数，**不是条目数，不是损失的命中数，也不是可节省时间**。同一条目可能此前已被使用；被丢弃后也可能根本没有再次查询。

因此不能直接推导：

- 大部分缓存条目从未被使用。
- JavaOperationLower 是没有净收益的主要原因。
- 只要保留 DT／JTA 就一定能反超。

可以提出的下一步是记录丢弃条目和后续查询之间的对应关系，再估计可恢复的收益。是否能 preserve 还需先证明 DT、LVI 和类型缓存的正确维护。

## 4. 真实流水线与真实应用要分开

本轮确实执行完整生产 `jeandle<O3>`，没有关默认内联和 PEA。但输入来自 6 个合成 Java 程序及其触发编译的 JDK 方法，不是实际应用样本。

76 份记录中 12 份在 ORIGINAL 回放失败，64 份入选，覆盖率为 84.2%。本次只核对了拒绝记录，不能仅凭其在 ORIGINAL 失败就证明每个根因均已独立排除本轮变更。

入选语料中没有三种模式都为零查询的样本。因此负对照仍不完整，不能声称已经验证零查询方法的全部额外成本。

原方案建议原生批量 runner 和实际应用输入；本次采用单样本 opt 子进程和合成 Java 输入。两者应记作执行范围差异，而非默认视为全部达成。

## 5. JVM 结果的矛盾和限制

### 5.1 三种模式实际都执行了

`jvm/jvm_compile_cost_summary.md` 有三种模式的受控组和后台组结果，jtreg 也有三种模式的 argv 和轨迹。原报告“只跑 cross_pass 完整 CITime 对照／未测 pass-local JVM 行为”的未覆盖说明与这些证据矛盾，整理版不沿用。

### 5.2 不是后台组所有区间都跨零

受控组的主要指标均未显示稳定加速。后台组 PASS-LOCAL→CROSS-PASS 的总编译时间和应用时间区间不跨零；原报告摘要中“两组主要指标均跨零”的概括不准确。

但后台组编译次数及具体任务可能不同，且采用并发 elapsed 计时，所以这些正向数字不能单独归因于缓存。将总时间除以编译次数，也不能保证比较了同样的方法、大小和编译尝试；没有匹配任务的证据时，不应声称归一化已经消除了混淆。

### 5.3 失败和重试

`scripts/jvm_compile_cost.py` 会记录失败并重试。受控组有 3 次、后台组有 4 次失败，成功完成后进入性能汇总。因此结果是成功运行条件下的计时，失败率需要另列。

原报告基线探测中，javac 为 2/8 对 2/8，jimage 为 2/8 对 3/8，不能写成“崩溃率相同”。已有基线也崩溃，支持“存在既有稳定性问题”，但不足以单独证明所有失败与本轮改动无关。

## 6. 后续引用建议

可以引用的主要事实：

1. 小型用例已验证下游首次查询命中和修改后的 Base 保留。
2. 完整生产流水线的合成 Java 语料中，Base 插入减少、Final 命中增加。
3. 整体相对 ORIGINAL 未测出稳定收益；相对 PASS-LOCAL 本次测到小幅变慢。
4. jtreg 真实子 JVM 中也验证了缓存复用；受控编译计时尚无稳定收益。
5. profiling 提示本批输入中 JTA 占比小，并指出待进一步调查的生命周期断点。

暂不引用为已证实结论的表述：

- “编译加速 38%”。
- “真实应用已证明收益／无收益”。
- “JavaOperationLower 就是性能瓶颈”。
- “只要修改 preserve 就能反超”。
- “pass-local 在所有场景下更优”。
- “全部失败都已证明与改动无关”。
