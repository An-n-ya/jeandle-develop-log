# JavaType 新版 V2 五版本性能复测

日期：2026-11-03。服务器：`annya@100.122.220.40`。本次针对 `feat/javatype-final-cache` 的 11 月 2–3 日缓存简化，重跑原报告全部 10 个场景，同时保留旧 V2 作为第五个对照。旧报告和历史数据未覆盖。

## 结论

新版 V2 相对旧 V2，在 **9 / 10 个场景显著改善**：5 个完整 opt 场景的 CPU 成本降低 **14.80%–19.35%**，其余 4 个微基准降低 **29.43%–35.53%**。唯一回退是“不同块无关修改”，成本增加 **51.18%**。

新版在全部 10 个场景仍显著慢于 V1 和 null-edge。相对无缓存，6 项更快、4 项更慢；后者是 leaf-static、virtual-cfg 和两个修改场景。因此本轮简化确有收益，但尚未追平旧缓存，并损失了不同块修改后的 Final 复用。

每场景、每版本 2 批 × 32 次诊断查询，诊断不进入正式时间：

| 同块无关修改 | 新版 V2 | 0 | 0 | 2176 |
| 不同块无关修改 | 旧 V2 | 62 | 0 | 2176 |
| 不同块无关修改 | 新版 V2 | 0 | 0 | 2176 |

新版 `getCachedJavaType` 在 Final 命中时直接返回。`JavaTypeCache::invalidate` 在完成 Base/Defined 的处理后，无条件失效 Facts 与 Final（该提交 `llvm/lib/Analysis/Jeandle/JavaTypeCache.cpp:469–470`）。这与不同块无关修改场景中 Final 命中从 62 次降至 0 次一致。此场景新旧 oracle 回调均为 2176 次，因此不能把回退解释成“oracle 回调次数增加”；新版还失去了 Final 结果复用，重新执行了求解工作。

前三个无修改微基准的新旧 V2 Final/Facts 命中数和 oracle 次数一致；时间下降没有依赖命中次数增加。具体各项开销占比未做 profiling，不能凭这些计数进一步量化归因。Facts 在 V1 与 V2 之间含义不同，不按命中次数直接排名。

## 方法、验证和审计

- 复用原报告 5 个 1024 函数 opt 输入及 callback、Pass 管线；另外 5 个 native 场景的 guard、上下文与修改序列不变。全部输入哈希须与原实验相同。
- raw/base/null/旧 V2 的 opt 与 replay 二进制直接复用原实验，开始前校验完整版本记录及二进制 SHA256，结束再次检查。未重建、切换或修改三个原有工作目录。
- 新版在独立 detached worktree 构建；使用同一 GCC 工具链、Release、O3/NDEBUG、关闭断言、静态链接。驱动仅适配已重命名的缓存接口，保留 StableOracleEpoch、32 次查询与修改通知顺序。新版 fixture 保留相同构造代码，去除已删除的旧 API 所对应的未使用成员/辅助方法。
- native 每版本每场景执行 64 次诊断查询，逐次与该版本原始 `getJavaType` + 新建 DT/AC/LVI 的完整 JavaType 对比，且要求 class 22。所有版本输出的 fixture IR 字节一致；V1 不允许 SkipVerification。
- opt 五版本最终 IR 逐字节一致；每版本独立 verification 与 diagnostic 输出也逐字节一致。raw 明确启用禁缓存开关，diagnostic 的 bypasses 大于零。
- 正式计时关闭统计、诊断和差分验证。固定 CPU 8、SMT 兄弟 9，不更改 governor 或系统服务，移除 LD_LIBRARY_PATH。每场景先做 3 轮预热 + 15 对 V1/V1 A/A，再做 3 轮预热 + 31 轮五版本随机交错，全部串行；随机种子 20261103。
- native 按版本分别校准批次数，目标约 360ms CPU；比较固定 32 次查询批次的归一化成本。使用原实验 4000 次 bootstrap 的 95% CI；区间须完全越过该行 A/A 绝对变化 P95，且所有正式样本至少 200ms CPU，才判改善/回退。

审计通过：**1850 个正式 A/A/比较样本，最短 CPU 244.51 ms**；25 组 native 诊断/输入一致性检查通过，10 个场景均完成；本机又从原始采样独立复核 10 组时间中位数与 100 组配对变化，`SUCCESS`、`PIPELINE_SUCCESS` 与 `audit.json` 齐全。

旧实现存在已知的其他精度/正确性问题；本次合成负载通过，不代表可仅凭性能恢复所有旧语义。新版对无缓存的比较也包含引擎版本差异，不是新版关闭缓存的消融。
